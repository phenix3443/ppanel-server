# 订阅周期与 Apple 有效期管理

订阅模块现已支持按经过验证的明确起止时间发放权益。Apple 管理的订阅使用专用周期同步入口，普通支付继续沿用现有时长规则，并在发放权益的同一事务中保存对应周期。

Apple IAP 的范围限定为标准月付和年付自动续费订阅，不包含固定时长或非自动续费 IAP。普通支付渠道原有的套餐时长类型继续保留。

## 已实现的范围与调用前提

`subscription.Service.ReconcileEntitlement` 接收 billing 模块传入的内部命令 `ReconcileEntitlementCommand`。该命令没有对应的 HTTP 接口，负责将已经验证、整理的支付状态更新到本地订阅，不承担 Apple 交易验签或服务器通知接收职责。

调用前，billing 模块必须完成以下步骤：

1. 验证 Apple 签名凭据、应用、环境、商品及账号绑定。商品映射必须对应标准周期为一个月或一年的自动续费商品。传入 `Mode = auto_renewable`，以及 `BillingInterval = month` 或 `year`；其他值会被拒绝。
2. 持久化支付平台交易及对应的已支付订单。订单必须使用 `Method = AppleIAP`，将已验证的交易 ID 写入 `TradeNo`，且订单的用户、套餐必须与命令一致。
3. 综合交易历史、撤销、升级及当前状态，计算出**当前实际生效的周期**。不能把已退款的历史交易作为当前订阅状态提交。
4. 为整理后的状态快照分配持久化、单调递增的版本号，并按订阅串行处理。通知到达顺序和 Apple 原始 `signedDate` 都不能直接作为这个版本号。
5. 持久化可重试的权益发放事件。处理失败时必须重试，包括数据库提交后的缓存清理失败。账号或名额冲突属于可恢复的交付失败，不能据此否定已经验证的购买事实。

后续 Apple 适配层仍需实现上述步骤，以及商品映射、StoreKit 交易确认与恢复购买、Notifications V2、定时对账、退款记账和订单完成流程。当前权益基础能力尚不足以启用完整的 Apple 支付。

## 状态与数据存储

`subscription_entitlement` 保存最近一次接受的支付平台状态快照，包括来源、作用域、订阅标识、本地所属用户、计费模式、状态、版本号、当前周期、自动续费开关、宽限期截止时间和撤销时间。作用域必须统一包含应用和环境，沙盒环境 Sandbox 与生产环境 Production 必须隔离。

`subscription_period` 保存明确的周期起止时间、来源交易、订单、套餐、计费周期、流量额度快照，以及该周期是否执行过流量重置。其 ID 根据来源、作用域和交易 ID 生成。同一交易不能重复发放权益，也不能通过更换用户或订阅标识绕过该限制。

`subscription_entitlement_revision` 将每次接受的状态快照保存为审计记录，包括撤销及撤销后的恢复。该表独立于运行任务使用的 inbox，不受 inbox 清理周期影响。

`user_subscribe` 继续保存节点和客户端使用的订阅状态。`ExpireTime` 表示实际允许访问的截止时间，不一定等于付费周期结束时间。历史订阅和本地管理订阅的 `EntitlementSource` 为空，Apple 管理的订阅为 `apple`；订阅响应 DTO 中也会返回这个来源字段。

| 状态快照 | 访问截止时间与处理行为 |
| --- | --- |
| 有效 | 使用明确的周期结束时间，不额外累加本地时长 |
| 宽限期 | 使用已验证的宽限期截止时间，付费周期结束时间仍保存在周期记录中 |
| 扣款重试或已过期 | 不提供有效权益；如果传入的付费截止时间仍在未来，则拒绝该状态 |
| 已撤销 | 停用访问，访问截止时间不晚于实际撤销时间 |
| 关闭自动续费 | 不缩短当前仍然有效的周期 |
| 更新版本的撤销恢复或订阅恢复 | 根据整理后的状态快照重新计算访问权限 |
| 较旧版本 | 不修改状态，但仍重试缓存清理 |
| 版本相同、内容不同 | 作为冲突拒绝处理 |

支付平台时间戳统一按 UTC 毫秒精度保存。尚未开始的周期不能作为当前权益提交；billing 调度器需要保留预约变更，并在其生效时投递新的状态快照。

## 月付、年付订阅与流量额度

IAP 仅接受 `auto_renewable`。`month` 和 `year` 商品均使用 Apple 提供的明确起止时间。不能根据实际相隔天数推断商品周期，也不能使用本地加月、加年的结果替代 Apple 日期：试用、月末日期、套餐升级及续费延期都可能改变单笔交易的实际时长。

`AutoRenew = false` 仍然表示自动续费商品，只是用户已关闭下一次续费，因此该状态可以正常同步。

计费周期按交易保存，同一交易重放时不能修改。经过验证的支付平台状态确认变更已经生效后，新的交易可以在同一订阅链中将月付切换为年付。未来生效的变更仍由 billing 调度器负责。不同订阅标识对应的权益相互独立，并继续遵守现有单订阅模式和套餐名额限制。

固定时长购买的叠加、固定时长退款后的区间重排，不属于本次 Apple IAP 的实现范围。

有效期同步与流量重置分别处理。一笔交易只有在首次接受其有效周期、明确要求重置、且套餐没有独立日历重置规则（`ResetCycle == 0`）时，才会触发周期流量重置。重复处理、自动续费开关变化、宽限期更新和退款撤销都不会再次重置流量。

按月或按年定时重置流量的套餐继续使用独立的日历调度。商品配置后续发生变化时，已有周期仍使用当时保存的流量额度快照。

支付平台状态更新会保留管理员停用状态。流量耗尽仍会阻止访问，只有符合规则的新周期实际发放了新额度后才可能恢复。过期检查和流量重置任务在写入时会重新检查当前记录，避免旧的任务结果将刚续费的订阅判为过期，或重新启用已经撤销、停用的订阅。

## 本地操作与兼容性

- 现有订阅、历史订单和 inbox 记录继续按本地业务处理。迁移不会推断历史支付来源，也不会补造旧周期。
- 新的普通购买和续费会在发放权益的同一事务中保存周期记录。即使 inbox 已被清理，持久化的交易标识仍能防止重复发放。
- Apple 管理的订阅拒绝普通续费、付费流量重置、折抵、退回站内余额、后台通用订阅编辑及单独删除订阅。需要暂停服务时，可以使用管理员停用操作。
- 定时赠送时长或流量重置任务会跳过 Apple 管理的订阅，并记录跳过结果。独立的账号赠送余额行为继续保留。
- 按站内价格发送的到期提醒不再包含 Apple 管理的订阅。Apple 专用的续费、扣款失败等通知由后续适配层负责。
- 凭据和管理员停用状态仍可修改，受保护的写入条件会阻止这些操作覆盖支付平台管理的到期时间或套餐。
- 本地时长计算继续保留现有月末和不限时规则，但不能用于推算 Apple 到期时间。

## 部署与验证

PostgreSQL 和 MySQL 均已提供功能迁移编号段中的 `03000_subscription_entitlements`。使用新版后端前必须先执行该迁移，现有记录默认仍由本地管理。

回滚迁移会删除权益历史。启用 Apple 权益发放后，如需回滚，必须先单独制定数据停用或导出流程。本次改造未对生产数据库执行迁移。

测试默认使用真实 SQLite 事务。将 `ENTITLEMENT_TEST_POSTGRES_DSN` 指向**隔离的测试数据库**，即可在 PostgreSQL 上运行同一套测试，包括并发版本更新和交易归属冲突测试。每个测试会创建并删除自己的 schema。示例：

```sh
go test ./...
ENTITLEMENT_TEST_POSTGRES_DSN='host=127.0.0.1 port=55432 dbname=entitlement_test sslmode=disable' \
  go test -race ./internal/module/subscription/internal/fulfillment -count=1
```
